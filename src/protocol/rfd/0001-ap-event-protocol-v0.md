# RFD: AP event protocol V0

- Status: Draft
- Owners: src/protocol
- Created: 2026-05-19
- Updated: 2026-05-19

## Summary

AP event protocol V0 defines the simulator-facing event vocabulary used before real module feedback
transport exists. It is an AP ingestion contract, not the physical infrared module wire protocol.

## Motivation

AP development needs a stable event shape so `src/protocol`, `src/core`, `src/ap_runtime`,
`src/storage`, `src/server`, and `src/simulator` can be built and tested before module firmware is
ready.

## Guide-level explanation

Every AP event uses a common envelope with a type-specific payload. The AP validates the envelope
before game rules see the event.

```json
{
  "schema_version": 0,
  "event_id": "01J00000000000000000000000",
  "event_type": "hit",
  "battle_id": "battle-001",
  "source_id": "module-red-01",
  "sequence": 42,
  "occurred_at_ms": 1730000000000,
  "payload": {}
}
```

## Reference-level explanation

### Common envelope

| Field | Type | Required | Meaning |
| --- | --- | --- | --- |
| `schema_version` | integer | yes | Protocol schema version. V0 is simulator-only. |
| `event_id` | string | yes | Globally unique event id generated by sender or simulator. |
| `event_type` | string | yes | One of the event types below. |
| `battle_id` | string | yes | AP battle session id. |
| `source_id` | string | yes | Module, simulator, or AP component that emitted the event. |
| `sequence` | uint64 | yes | Monotonic per `source_id` sequence for deduplication and diagnostics. |
| `occurred_at_ms` | int64 | yes | Sender-observed event time in Unix milliseconds. |
| `payload` | object | yes | Type-specific payload. |

### `player_joined`

Registers a player in a battle.

```json
{
  "player_id": "p-red-01",
  "display_name": "Red 01",
  "team_id": "red",
  "module_id": "module-red-01"
}
```

### `battle_started`

Starts scoring and live recording for a battle.

```json
{
  "mode": "team_deathmatch",
  "duration_ms": 600000
}
```

### `shot`

Records that a player fired.

```json
{
  "player_id": "p-red-01",
  "weapon_id": "rifle-01",
  "ammo_after": 29
}
```

### `hit`

Records that a target was hit. In V0 this may be simulator generated.

```json
{
  "attacker_player_id": "p-red-01",
  "target_player_id": "p-blue-02",
  "weapon_id": "rifle-01",
  "damage": 10,
  "hit_zone": "torso"
}
```

### `player_state`

Updates AP-visible player state.

```json
{
  "player_id": "p-blue-02",
  "health": 70,
  "ammo": 12,
  "alive": true
}
```

### `battle_ended`

Ends the battle and freezes final scoring.

```json
{
  "reason": "time_limit"
}
```

### `battle_paused`

Pauses an active battle. Gameplay events are rejected while paused.

```json
{
  "reason": "operator"
}
```

### `battle_resumed`

Resumes a paused battle.

```json
{}
```

### AP validation rules

- Reject unsupported `schema_version`.
- Reject missing or malformed envelope fields.
- Reject duplicate `event_id` within the battle event log.
- Reject stale duplicate `sequence` for the same `source_id` unless the payload is byte-identical.
- Reject events for unknown battles except battle creation/control events accepted by the AP runtime.
- Reject hit events whose attacker or target is not registered in the battle.

## Drawbacks

- V0 is JSON and simulator-oriented, so it is not final module transport.
- Some validation rules depend on runtime state, not only protocol shape.

## Rationale and alternatives

A JSON envelope wins for AP V0 because it is easy to POST, inspect, store in JSONL, and generate from
simulators. Binary module transport is deferred until module feedback timing and reliability needs
are known.

## Prior art

- Event envelopes in realtime systems.
- `embedev` protocol modules that isolate message encoding from runtime behavior.

## Unresolved questions

- Whether `battle_id` should be optional for battle creation.
- Exact constraints for ID length and character set.
- Whether `occurred_at_ms` must be trusted, bounded, or treated as diagnostic only.

## Validation and rollout

- Unit: valid event parsing, required field failures, unsupported schema, unknown event type, payload
  shape mismatch.
- Module-local integration: simulator-generated event sequence validates through `src/protocol`.
- Cross-module integration: HTTP POST endpoint rejects malformed protocol messages.
- Migration or rollout: V0 remains AP-only until module transport RFD exists.
- Deferred gaps: binary module protocol, authentication, acknowledgements, and clock sync.
